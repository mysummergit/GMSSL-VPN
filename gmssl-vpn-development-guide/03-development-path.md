# 第 3 章：开发路线

> 本章回答：从两份开源代码出发，应该按照什么顺序，把各项能力组合成一个可验证的 GMSSL VPN？

## 本章目标

总体设计解决了“系统应该是什么样”，本章进一步解决“开发时先做什么、后做什么”。

这条路线不展开函数、接口和配置命令，而是把开发过程划分为四个可以独立验证的阶段。每个阶段都说明：系统从哪里出发、需要改变什么、主链路怎样运行、必须做出哪些技术决定，以及交付什么结果后才能继续。GM/T 0024-2023 从第一阶段开始约束设计，最后阶段负责汇总证据并完成标准收敛。

```mermaid
flowchart LR
    B["工程基线<br/>两端代码可以独立运行"]
    S1["阶段一<br/>TLCP 安全连接"]
    S2["阶段二<br/>单客户端 VPN"]
    S3["阶段三<br/>完整客户端—服务端"]
    S4["阶段四<br/>标准收敛与模式扩展"]

    B --> S1 --> S2 --> S3 --> S4
```

这不是项目排期，而是技术依赖顺序。TLCP 尚不稳定时加入 TUN，只会把协议问题和网络问题混在一起；单客户端链路尚未闭合时扩展多用户，也很难判断故障属于会话、策略还是转发。

## 3.1 先建立可回退的工程基线

正式改造前，先分别确认 OpenVPN 与 GmSSL 的基线能力可以运行。目的不是研究完两份源码，而是为后续问题建立清晰边界。

| 基线 | 需要确认的结果 | 后续用途 |
|---|---|---|
| OpenVPN 基线 | 虚拟网卡、地址配置、路由和基本转发可以工作 | 证明网络故障不是由改造前代码引入 |
| GmSSL 基线 | TLCP 客户端和服务端可以握手并传输应用数据 | 证明证书、套件和协议环境基本可用 |
| 联调基线 | 固定 OpenVPN、GmSSL 和自身代码的提交标识、构建方式、最小配置和日志位置 | 出现问题时可以复现、审查和回退比较 |

这一准备阶段只需要留下一个最小运行场景和一份基线记录。不要在这里提前设计完整产品，也不要把“两个示例都能运行”误认为二者已经完成集成。

## 3.2 路线总览

| 阶段 | 本阶段真正改变的内容 | 交付结果 | 进入下一阶段的门槛 |
|---|---|---|---|
| 一：TLCP 安全连接 | 用 GmSSL 建立符合目标协议要求的传输安全边界 | 一条可观察、可诊断、完成所需身份认证的安全通道 | 不依赖 VPN 功能即可稳定收发受保护数据 |
| 二：单客户端 VPN | 把 OpenVPN 的虚拟网络能力接到 TLCP 应用数据路径 | 一条完整的客户端—资源 IP 报文往返链路 | 地址、路由、报文边界和断连清理均可解释 |
| 三：完整客户端—服务端 | 让 VPN 接入会话绑定身份、地址、策略，并关联有效的 TLCP 连接 | 多客户端可隔离、可控制、可审计的系统主线 | 并发接入会话、访问控制、换钥和异常清理可验证 |
| 四：标准收敛与模式扩展 | 收敛产品安全与验证证据，并按产品范围扩展网关模式 | 可按标准要求逐项复核的完整实现 | 每项结论均能指向设计、实现和验证证据 |

这张表可以直接作为开发主线。每完成一个阶段，应冻结一个可运行版本，再开始引入下一层复杂度。

## 3.3 阶段一：建立 TLCP 安全连接

### 从哪里开始

这一阶段只处理客户端与服务端之间的安全连接，不引入 TUN、虚拟地址和访问策略。OpenVPN 的网络能力暂时放在边界之外，先把 GmSSL 提供的协议与密码能力形成一条可信通道。

### 系统怎样变化

```text
普通网络连接
    ↓
TLCP 1.1 握手
    ↓
服务端身份认证、按策略进行的客户端身份认证与密码套件协商
    ↓
受保护的双向应用数据
```

开发时需要形成清楚的安全边界：连接与事件处理可以复用既有工程能力，但证书验证、握手、记录保护和密钥状态由 TLCP 路径负责。协议错误不能被简单转换成一次普通网络断开，否则后续无法判断失败发生在哪个安全阶段。

### 必须做出的技术决定

| 决定 | 需要回答的问题 |
|---|---|
| 证书模型 | 签名证书和加密证书如何配置，服务端身份如何验证，何时请求并验证客户端证书？ |
| 套件策略 | 主开发套件是什么，标准所列套件怎样形成后续覆盖矩阵？ |
| 后端边界 | 软件密码后端与独立密码部件是否通过同一抽象边界接入？ |
| 状态与错误 | 怎样观察握手阶段、协商结果、记录保护状态和关闭原因？ |

此处不需要一次完成所有产品能力，但设计不能封死后续的密码套件扩展和独立密码部件接入。

### 本阶段交付什么

- 一个可重复启动的 TLCP 客户端—服务端场景；
- 一条受保护应用数据的双向收发路径；
- 能说明协议版本、协商套件、认证结果和失败原因的日志；
- 证书无效、套件不匹配等代表性失败场景；
- 一份已支持、待支持和待验证的密码套件清单。

阶段完成的判断不是“握手函数返回成功”，而是正常连接和典型失败都可观察、可重复、可解释。

## 3.4 阶段二：建立单客户端 VPN

### 从哪里开始

现在已有一条稳定 TLCP 通道，下一步只接入一个客户端，把安全连接变成最小可用 VPN。这个阶段第一次真正组合 OpenVPN 与 GmSSL。

### 系统怎样变化

```text
客户端应用
   ↕
客户端 TUN
   ↕  IP 报文
VPN 载荷适配层
   ↕  TLCP application_data
服务端会话与转发
   ↕
受保护网络
```

OpenVPN 侧保留虚拟网卡、地址、路由和转发等工程能力；GmSSL 侧保护传输通道；中间的适配层把 IP 报文放入 TLCP 应用数据，并将收到的数据交回正确的网络路径。这一层是两份开源能力真正发生组合的地方。

### 必须做出的技术决定

| 决定 | 需要回答的问题 |
|---|---|
| VPN 载荷边界 | 控制信息与 IP 报文如何区分，接收端怎样识别完整载荷？ |
| 地址绑定 | 虚拟地址由谁分配，为什么该地址只能属于当前安全连接？ |
| 报文尺寸 | 怎样处理 MTU、较大报文和通道读写压力，避免静默丢包？ |
| 生命周期 | 连接建立、网络就绪、断开和异常退出分别怎样改变转发状态？ |

客户端—服务端主路径使用 TLCP `application_data` 承载本指南定义的简洁 VPN 载荷。可以借鉴 OpenVPN 的成熟工程处理，目标通信路径与其私有控制通道、ACK 和数据通道协议保持分离。

### 本阶段交付什么

- 客户端能够获得并使用虚拟地址；
- 一个 IP 报文能够从客户端 TUN 到达目标资源，并沿原接入会话返回；
- 日志能够关联 TLCP 连接、VPN 接入会话、虚拟地址和报文方向；
- 路由错误、目标不可达和异常断连能够被区分；
- 断连后地址、转发项和临时敏感状态能够清理。

“能够 ping 通”只是最小现象。真正的阶段门槛是：开发者能够沿链路解释报文从哪里进入、怎样受到保护、由哪个接入会话授权并转发，以及连接消失后哪些状态必须失效。

## 3.5 阶段三：形成完整客户端—服务端系统

### 从哪里开始

单客户端证明了数据路径可以闭合，但还没有解决真实系统里的多用户隔离、访问控制、密钥更新和审计问题。阶段三将“能传输”推进为“安全可管”。

### 系统怎样变化

系统的核心对象从一条数据链路升级为 VPN 接入会话，并与 TLCP 连接和密码状态保持绑定：

```text
VPN 接入会话
├── 用户或设备身份
├── 虚拟地址与路由状态
├── 当前访问策略
├── 换钥时间与流量条件
├── 创建、在线、关闭和清理状态
└── 当前有效的 TLCP 连接
    └── 当前密码状态
```

所有转发和策略判断都应从这一个安全上下文出发。服务端不能只根据报文中看起来合法的源地址放行，而要先由 TLCP 连接找到 VPN 接入会话，再确认身份、地址和策略之间的绑定关系。

### 必须做出的技术决定

| 决定 | 需要回答的问题 |
|---|---|
| 会话归属 | TLCP 连接怎样对应一个身份、虚拟地址和策略集合？ |
| 并发隔离 | 多客户端同时在线时，地址、数据、密钥和清理操作怎样互不串扰？ |
| 访问控制 | IP、端口、时间和 URL 策略分别在哪条资源访问路径执行？ |
| 密钥更新 | 时间与流量触发如何共同生效，更新期间怎样保持会话一致？ |
| 审计边界 | 哪些认证、策略、换钥、异常和管理事件必须留下记录？ |

URL 控制需要能够看到 Web 请求目标的资源访问路径，不能只依赖三层 TUN 转发；密钥更新则应被设计为会话生命周期的一部分，而不是独立的定时任务。

### 本阶段交付什么

- 多个客户端能够同时建立各自独立的 VPN 接入会话；
- 身份、虚拟地址和访问策略能够稳定绑定；
- 允许流量能够到达资源，拒绝流量被阻断并留下原因；
- 达到时间或流量条件时能够更新 TLCP 安全参数，按标准第 6.5 节建立并切换新的工作密钥；
- 正常退出、超时和异常断开都能完成资源与敏感状态清理；
- 认证、上线、访问拒绝、换钥和下线形成连续审计链。

完成这些结果后，客户端—服务端模式形成完整产品主线。阶段四将在这条主线上收敛密码部件、产品管理、性能和检测证据，并按产品声明扩展网关—网关模式。

## 3.6 阶段四：完成标准收敛与模式扩展

### 从哪里开始

前三个阶段已经按照 GM/T 0024-2023 建立稳定的客户端—服务端主线。阶段四汇总各阶段形成的标准追踪关系，关闭产品安全、性能和验证缺口；产品声明支持网关—网关模式时，同时完成独立的 `site2site` 协议路径。

### 按五个工作包收敛

| 工作包 | 主要内容 | 应形成的结果 |
|---|---|---|
| 协议覆盖 | TLCP 版本、密码套件、记录保护、异常处理和互操作 | 协议能力与验证状态清晰可追踪 |
| 密码与密钥 | 独立密码部件、硬件随机源、私钥保护、更新周期和密钥销毁 | 密钥全生命周期能够复核 |
| 产品能力 | 管理员、配置、证书管理、访问控制、日志、自检、监控和性能 | 产品要求能够进入实际检查场景 |
| 软件安全 | 固定源码基线、关键模块自主实现、差异审查、可复现构建、漏洞修复和系统加固 | 安全协议及管理软件具备独立维护和审查能力 |
| 模式扩展 | 按产品范围实现 `site2site(80)`、command/data、保护域和双向转发 | 独立于客户端模式的标准协议路径 |

网关—网关模式可以复用底层网络、密码后端和部分会话管理能力，但使用标准规定的 `site2site` 记录形成独立路径，并将连接身份与两端保护域绑定。

### 本阶段交付什么

- 标准要求、设计位置、实现位置、验证结果和证据之间可以相互追踪；
- 客户端—服务端模式的密码套件、换钥、访问控制和产品安全要求有明确状态；
- 产品声明的工作模式均已形成完整实现；支持网关—网关时，可以在绑定的保护域之间传输完整 IP 包；
- 软件开发后端与目标密码部件的差异得到关闭或明确记录；
- 最大并发连接数、每秒新建连接数、最大并发用户数和加解密吞吐率有一致的测量口径；
- 未覆盖项保持明确，不用局部成功替代整体符合性结论。

这一阶段完成后，系统才具备进入完整验证和符合性评估的条件。

## 3.7 把阶段转化为开发任务

每个开发任务都应同时写清四项内容：

| 项目 | 示例含义 |
|---|---|
| 输入条件 | 依赖哪个已经稳定的连接、会话或网络能力 |
| 系统变化 | 新增或改变哪个边界、状态或运行链路 |
| 可运行结果 | 开发完成后能实际观察到什么行为 |
| 完成证据 | 用日志、状态、抓包摘要或测试结果证明什么结论 |

例如，“支持工作密钥更新”需要同时覆盖触发条件、TLCP 安全参数更新、按第 6.5 节计算新工作密钥、安全切换、旧状态退出以及时间和流量两种触发结果。这样才能形成完整、可验证的开发任务。

这种写法不要求任务文档沉入实现细节，却能防止开发结果停留在“代码已经写了，但不知道是否形成完整能力”。

## 3.8 每阶段保留四类成果

| 成果 | 回答的问题 |
|---|---|
| 简短设计记录 | 这一阶段改变了哪个系统边界？ |
| 最小运行场景 | 主链路是否真的能够运行？ |
| 观察与验证记录 | 为什么相信它按预期工作？ |
| 缺口清单 | 哪些能力尚未完成，不能得出什么结论？ |

这些成果不必写成长篇文档。它们的价值是让下一阶段有可靠起点，也让后续标准验证能够找到真实依据。

## 本章结束时

读者应当能够：

1. 建立 OpenVPN 与 GmSSL 各自可运行的工程基线；
2. 按 TLCP、安全数据路径、完整客户端系统和标准收敛的顺序推进；
3. 知道每个阶段真正改变的是哪一层系统能力；
4. 把阶段目标拆成带运行结果和完成证据的开发任务；
5. 区分“阶段已经跑通”和“产品已经符合 GM/T 0024-2023”。

下一章会用一个简明验收框架，把这些阶段成果对应到协议正确性、VPN 可用性和标准符合性证据。
